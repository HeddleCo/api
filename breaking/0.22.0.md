# 0.22.0 additive surface — NotificationService + discussion-turn streaming/provenance

This release is **purely additive**: a new file, a new `PLANNED` service, new
enum values, and new message fields at their next free numbers. No RPC or
message is removed, renamed, or renumbered, and no advertised maturity is
withdrawn. `buf breaking --against '.git#ref=origin/main'` reports nothing —
this document is a release record, not a break report.

## E6 — `NotificationService` (new `notification.proto`, PLANNED)

A dedicated per-recipient notification surface. A `Notification` **references** a
FeedItem (`feed_item_id` → attention.proto `FeedItem.item_id`) rather than
copying it. Deployment target `WEFT`, service maturity
`SERVICE_MATURITY_PLANNED` — weft has not built it yet.

- `CapabilityArea.CAPABILITY_AREA_NOTIFICATIONS = 15` (contract.proto, next after
  `ASYNCHRONOUS_OPERATIONS = 14`).
- New enums: `NotificationKind` (values `1..6` mirror `FeedItemKind` numbers and
  names; `10 MENTION`, `11 DISCUSSION_REPLY`, `12 ACCOUNT_SECURITY`,
  `13 STEER_HELD` are notification-only), `NotificationChannel`
  (`IN_APP`/`EMAIL`/`WEB_PUSH`), `NotificationRouting`
  (`IMMEDIATE`/`DIGEST`/`MUTED`), `DigestCadence`
  (`OFF`/`HOURLY`/`DAILY`/`WEEKLY`), `ActorOrigin` (`ANY`/`HUMAN`/`AGENT`, keyed
  on `actor_agent_id` empty/non-empty), and `NotificationDeliveryStatus`.
- New messages: `Notification`, `NotificationDelivery`, and the full preference
  matrix (`NotificationPreferences`, `ChannelRule`, `SpoolPreferenceOverride`)
  plus request/response pairs.
- Service `NotificationService` with six RPCs: `ListNotifications`,
  `SubscribeNotifications` (dedicated per-recipient resumable stream),
  `MarkNotificationRead`, `GetNotificationPreferences`,
  `SetNotificationPreferences`, and `Unsubscribe`. The five per-recipient RPCs
  use `authorization_scope_source: CALLER_SUBJECT` (a notification belongs to
  its recipient, not a repo's readers); `Unsubscribe` is
  `AUTHORIZATION_ACCESS_PUBLIC` — the in-body `unsubscribe_token` is the whole
  proof.

## E5 — live discussion turns on the repo_events plane

Discussion turns reuse the existing `SubscribeRepoEvents` / `repo_events` live
plane instead of a new stream.

- `RepoEventKind` (new enum in repository.proto): `REPO_EVENT_KIND_UNSPECIFIED = 0`,
  `REPO_EVENT_KIND_DISCUSSION_TURN = 1`. `RepoEvent.event_type` (string) remains
  authoritative on the wire; `RepoEvent.kind = 15` is an additive **typed
  projection** of it, `UNSPECIFIED` for any `event_type` the enum does not yet
  name. (The original design assumed a pre-existing `RepoEventKind` enum;
  `event_type` was in fact free-form string, so the enum is introduced here.)
- `DiscussionTurn.turn_seq = 6` (`uint64`, per-discussion monotonic sequence)
  and `DiscussionTurn.turn_id = 7` (stable identity) — server-minted turn
  identity in state_review.proto.

## E3 — imported-discussion turn provenance

On `DiscussionTurn` (state_review.proto), additive provenance for imported/PR
conversations, all empty for a native turn:

- `external_author_display = 8` (presentation text, never an auth subject)
- `external_author_id = 9` (source system's stable author id)
- `source_url = 10` (deep-link to the original)
- `original_created_at = 11` (`google.protobuf.Timestamp`; `posted_at` remains
  the import time)

## Why no compatibility shim

Everything is additive, so no consumer breaks and there is nothing to shim.
The `PLANNED` maturity on `NotificationService` advertises the contract without
claiming a producer serves it; weft's handlers land in a companion PR after
0.22.0 releases.
