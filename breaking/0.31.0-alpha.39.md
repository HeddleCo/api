# 0.31.0-alpha.39: creator-only re-reads of pending invitation codes

Owner decision (2026-10-05): creators can copy the original invitation link
repeatedly until it is claimed. This release adds dedicated hosted unary RPCs:

| RPC | Request | Response |
| --- | --- | --- |
| `IdentityService/GetSignupInvitationCode` | `GetSignupInvitationCodeRequest.invitation` (`RecordRef`, tag 1) | `GetSignupInvitationCodeResponse.redemption_secret` (`bytes`, tag 1) |
| `SpoolService/GetInvitationCode` | `GetInvitationCodeRequest.invitation` (`RecordRef`, tag 1) | `GetInvitationCodeResponse.redemption_secret` (`bytes`, tag 1) |

Both use authenticated-principal signing, proof of possession, safe retry,
caller-bound authorization and hidden existence. The creator is the immutable
authenticated account subject captured at creation. For spool invites this is
the original inviter only; other current admins receive `NOT_FOUND`. The host
must check credential authority/attenuation and creator equality, never trust
the request reference or public inviter handle as authority.

The original code is returned only while unredeemed, unrevoked and strictly
unexpired. Terminal creator reads return empty; unknown/non-creator references
uniformly return `NOT_FOUND`. Legacy hash-only and non-link handle/account
invitations return empty without minting a replacement. Creation responses keep
their existing separate secret field. `SignupInvitation`, `InvitationRecord`,
lists, observations, inbox, previews and receipts remain code-free. Dedicated
reads avoid putting capabilities in the shared view state or its caches.

The [normative host contract](../docs/alpha-v2/invitation-codes.md) requires
retrievable encrypted-at-rest storage under the host KEK using AEAD bound to
stable invite reference, immutable creator and distinct signup/spool purpose,
plus deployment/version. Redemption still checks a hash in constant time.
Ciphertext is destroyed on redeem, revoke or expiry, including retry/outbox
copies; lifecycle reads serialize with those transitions. Read attempts have
per-account and per-invite pacing limits and secret-free audit before release.
Responses must not be cached or traced. A DB + KEK compromise exposes pending
codes (accepted by the owner), bounded by expiry and terminal redemption checks.

Rust adds `v2::invitation_code::{validate_signup_invitation_code_response,
validate_invitation_code_response}` and `InvitationCodeReadContext`.
TypeScript exports `validateSignupInvitationCodeResponse`,
`validateInvitationCodeResponse` and `InvitationCodeReadContext` through
`@heddleco/api/v2/invitation-code` and the v2 barrel. They validate trusted
caller/creator subjects, valid timestamps and empty terminal responses;
they do not implement host authentication, persistence or encryption.

Shared vectors are in `tests/fixtures/invitation-code-reads.json`. They cover
another account/admin/recipient, repeated creator reads, redeem/revoke/expiry,
nanosecond equality, invalid timestamps, legacy empties and protobuf wire bytes.
Rust and TS recursively walk every service output to ensure a code never leaks
through a nested projection; only top-level create and creator-read responses
are permitted. `tools/verify-alpha39-guards.py rust` and `ts` individually
disable creator, redeem, revoke, expiry and expiry-equality checks, then inject
a secret into a shared record. Every mutation must fail real tests; restored
code must pass. Both guard runs are included in `./tools/verify.sh`.

## Fail-then-pass evidence

Red checkpoint `aab0ffad` used deliberately permissive response validators:
Rust exited 101 (3 passed, 3 failed) and TypeScript exited 1 (2 passed, 3 failed).
Non-creator reads and terminal disclosures were accepted. The implemented
validators pass the same vectors; the independent mutation probes also prove
revocation and expiry checks fail when disabled. These are API conformance
tests. Host AEAD storage/destruction, concurrency, rate-limit and audit
integration tests remain an obligation of the implementing host repository.

Release order is alpha.38 (PR #361) followed by alpha.39. Merge `origin/main`
after #361 lands, then advance all seven Rust/npm version files together.
Existing alpha.38 invitation and notification semantics are preserved.
