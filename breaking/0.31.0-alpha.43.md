# 0.31.0-alpha.43: Git branch names and spool deletion verification

Fixes HeddleCo/api#380, reported by tapestry#587 while importing
`dmtrkovalenko/fff`: `refs/heads/feat/mcp=timeout` made the entire import fail.
Rust and TypeScript now accept Git branch syntax, including `=`, `+`, `@`,
`,`, and non-ASCII UTF-8, in both permission scopes and result manifests.

## Origin of the restriction and encoding audit

The alphabet was introduced in commit
`639cf881a71e98a58623fcf80aa69bdc676b77f4` (api#296). That commit's contract
places the ASCII ref subset next to its explicitly “conservative” HTTPS
canonicalization policy. Neither its commit message nor the original contract
records a ref-specific delimiter, URL, filesystem, or signing rationale. The
evidence supports a conservative launch validation policy; a more specific
historical intent cannot be established from the checked-in record. The
associated [PR #299 review resolution](https://github.com/HeddleCo/api/pull/299)
(P2 #6) later describes applying ASCII to manifest refs to align them with
import refs while auditing UTF-8 bounds. That explains the second restriction
as validator parity, but supplies no alphabet-dependent encoding requirement.

The API does not embed refs in URLs, paths, storage keys, or display markup.
`src/import_authority.rs` uses `record!` string fields for branch limits,
committed slots, delegated operations and publication witness payloads.
`src/hybrid_codec.rs`'s `field!(..., s)` passes exact `str::as_bytes()` to
`counted`: u32 big-endian byte length followed by those bytes. TypeScript's
`v2-hybrid-codec.ts` STRING encoder does the same, refusing unpaired surrogates.
No delimiter escaping or signed encoding change is needed. Existing signatures,
digests, domains, protobuf tags and frozen authority/witness vectors retain
their bytes. Display escaping must never be written back into signed identity.

One genuine alphabet-dependent assumption was TypeScript's native string
ordering. UTF-16 orders supplementary characters before U+E000, while Rust's
UTF-8 order does the reverse. Scope validation, manifest validation, and both
progressive manifest reconstruction paths now compare unsigned UTF-8 bytes.
Manifest validation also applies the full Git branch rules, replacing the
separate prefix-plus-ASCII check which accepted invalid Git syntax.

## Decisions

- Names are literal full `refs/heads/<branch>` UTF-8 strings. The suffix follows
  `git check-ref-format --branch` rules; no normalization or context-dependent
  `@{-n}` checkout expansion. Exact `HEAD` and a leading `-` are refused; a
  short name of `@` is accepted.
- The existing **1024-byte maximum for the full ref, including the 11-byte
  prefix**, is retained as a resource bound. Git's syntax check itself has no
  maximum. Both validators measure UTF-8 bytes (TypeScript previously measured
  UTF-16 code units for branch limits). Valid overlength input returns `Bounds`;
  invalid syntax returns `Canonical` before the length check. Existing record,
  branch count and bundle limits also continue to apply.
- Git forbids ASCII controls 0x00–0x1f, DEL 0x7f, space and `~^:?*[\`, plus its
  path-component and sequence rules. Unicode controls outside those ASCII
  bytes, combining forms and bidi code points remain valid ref identities.
  Display safety is the UI's responsibility.
- Git itself stores byte names, but the existing protobuf `string` transport
  represents only valid UTF-8. Invalid UTF-8 is unrepresentable and must fail
  without lossy decoding. Rust strings enforce this; TypeScript additionally
  refuses lone UTF-16 surrogates. No normalization, case folding or replacement
  occurs before hashing/signing/comparison. A raw non-UTF-8 transport would
  require a separately designed wire change.

## Sley dependency choice

`sley-refs = 0.11.0` is an exact **dev dependency**, used as the executable
reference in conformance and property tests. Production retains a minimal
in-crate mirror, and TypeScript ports the same byte rules. A production
dependency would bring six Sley crates (`refs`, `config`, `core`, `formats`,
`pathspec`, `object`) plus `flate2`/`zlib-rs` into this transport-neutral crate.
Those crates contain filesystem, ref-store and configuration operations;
none is needed for string validation. `heddle-api` is already in Heddle's
WASM capability-verifier and thread-api dependency graphs. It uses std today;
no no_std promise was found. Keeping the reference dev-only avoids expanding
those consumers' production graphs or making ref-store portability a contract
requirement. `proptest` enables only its `std` feature, without fork/timeout.

Sley 0.11.0's `BranchRefNameBuf::from_full` checks the namespace and general
format but does **not** run its short-name leading-dash check. Use
`from_branch_name` for that check. Both constructors permit exact `HEAD`,
which Git's branch command refuses; the oracle and production validators add
that explicit branch-only check. `check_refname_format(full, false)` remains
the general-format reference. Tests pin and document these differences rather
than relying on the constructors' names to imply stronger validation.

## Conformance and release

Both languages read `tests/fixtures/import-branch-refs-v1.json`. It includes
all five requested previously rejected names, all forbidden ASCII controls
and punctuation, branch-specific failures, Unicode controls, normalization
distinctions, exact/overlength ASCII and multibyte boundaries, and an ordering
pair distinguishing UTF-8 from UTF-16. Frozen branch digests and a signed
Unicode manifest establish cross-language byte identity; normalizing a name
invalidates the signature. Rust also runs every representable vector against
Git and Sley, and 2048 cases each of random byte strings, ASCII strings and
Unicode scalar strings against Sley. Invalid byte strings are not lossily
converted into another input identity.

The tests were run against the old code first: Rust refused `reported_fff`
with `Canonical`; TypeScript failed each of the five required acceptance
vectors. The red commit is `e546fc8b`. Existing fixture files are unchanged.

Cargo, npm, root locks, both path-consumer nested locks and the normative docs
header move together to `0.31.0-alpha.43`. The owner-authorization conformance
lock pins a separate historical Heddle graph and has no local alpha.42 package;
it is unchanged. No wire change or Buf breaking override is required.
Tagging and publication belong to the orchestrator and are not performed here.

Consumers must repin and remove independent alphabet checks before all these
names can import end to end. See the
[Heddle/Weft audit with pinned file:line locations](0.31.0-alpha.43-consumer-impact.md).


## DeleteSpool: per-request passkey assertion (api#382)

`SpoolService.DeleteSpool` changes from `SIGNING_TIER_PROOF_OF_POSSESSION`
to `SIGNING_TIER_HUMAN_VERIFICATION`. The owner requires a passkey signature
on the deletion request itself, and weft already enforces `sig = "human"`.
This is a behavioral breaking change for clients choosing their proof from
the descriptor, even though protobuf messages, field tags and signing bytes
are unchanged. It applies to every advertised deployment target of this RPC.

Tapestry must send a **per-request WebAuthn passkey assertion**: populate
`CallContext.request_proof` with algorithm `webauthn`, signing identity,
timestamp, nonce and assertion signature, and populate
`CallContext.human_verification` with the assertion's client data,
authenticator data and user handle. Bind the WebAuthn challenge to the canonical
unary signing bytes for this exact method and encoded request, following the
existing human-tier verification protocol. A new passkey sign-in does not
satisfy this request assertion. Keep the current authenticated session during
step-up; a human-verification challenge must not itself end the session.
The original client operation ID still governs deletion deduplication.

Rust and TypeScript descriptor regressions require HUMAN_VERIFICATION for
DeleteSpool, PutGrant and PutReviewPolicy. They failed for DeleteSpool against
the old descriptor (Rust: ProofOfPossession versus HumanVerification;
TypeScript: 2 versus 3). The red commit is `7072911d`. The new
`unary-signing-human-alpha43.json` identifies its DeleteSpool route as
human-tier and preserves every field of the historical `unary-signing-v1.json`
vector. The historical fixture remains byte-identical for the continuity gates;
both languages verify parity, and canonical signing bytes remain unchanged.
Rust code, method catalogs and the binary descriptor regenerate at build time;
TypeScript code and descriptor options regenerate with `npm run generate`.
These generated outputs are build artifacts and are not checked into Git.
